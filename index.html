Introducción

2.1 · Propósito

El propósito de TANDAR-CNEA es resolver la gestión manual y desorganizada de las solicitudes de turno de irradiación en el acelerador TANDAR del Centro Atómico Constituyentes (CNEA).

Actualmente estas solicitudes se coordinan por canales informales (correo, WhatsApp, papel), lo que genera demoras, pérdida de trazabilidad y falta de un registro formal de aprobaciones. El sistema busca centralizar en una plataforma web el circuito completo: solicitud del investigador, evaluación del responsable de línea experimental, evaluación del administrador (Jefe de Operaciones) y, en caso de aprobación, la generación del documento formal de irradiación.

2.2 · Alcance

Incluye

  • Registro y autenticación de usuarios por rol.
  • Solicitud de turnos con fecha, horario, línea experimental y motivo.
  • Circuito de aprobación en cascada.
  • Calendario de disponibilidad por línea experimental.
  • Sistema de notificaciones.
  • Generación de documento o planilla Excel/PDF.

Fuera de alcance

  • Integración con sistemas documentales externos de CNEA.
  • Autenticación externa mediante Google.
  • Facturación, costos o presupuesto.
  • Aplicación móvil nativa.

2.6 · Resumen ejecutivo

TANDAR-CNEA es un sistema web desarrollado en PHP y MariaDB para gestionar el circuito de solicitud, evaluación y aprobación de turnos de irradiación. Reemplaza un proceso manual por un flujo digital con roles diferenciados, notificaciones automáticas, calendario de disponibilidad y generación de documentación formal.

Descripción general

3.1 · Perspectiva del producto

TANDAR-CNEA es un sistema nuevo, construido específicamente para digitalizar un proceso gestionado manualmente dentro de la CNEA. Funciona como una aplicación web independiente alojada en un nodo interno.

3.2 · Funcionalidad del producto

Autenticación según rol.
Calendario de disponibilidad.
Creación y evaluación de solicitudes.
Notificaciones.
Generación del documento final.
Historial de solicitudes.

Interfaz100% en español.

3.5 · Suposiciones y dependencias

  • Disponibilidad del nodo interno nginx + MariaDB.
  • Uso efectivo de la plataforma por los distintos roles.
  • Disponibilidad de una cuenta de correo para notificaciones, sujeta a las restricciones de red.

3.6 · Evolución previsible

  • Correo interno de CNEA o SMS.
  • Reportes estadísticos de uso.
  • Migración a servidor propio con HTTPS si se aprueba formalmente.

4.3 · Interfaces de usuario

Sistema 100% web, responsive, con identidad visual común y selector de tema claro/oscuro. Cada rol posee un panel específico y todos comparten calendario y notificaciones.

4.4 · Interfaces de hardware

No aplica. El sistema es puramente web. El único hardware involucrado es el navegador del usuario y el nodo provisto por la CNEA.

4.5 · Interfaces de software

Backend con PHP 8 sin framework, PDO y prepared statements. Composer incorpora PHPMailer y PhpSpreadsheet. Frontend construido con HTML, CSS y JavaScript vanilla, sin framework ni build step.

4.6 · Modelo de base de datos

MariaDB 11.4, motor InnoDB y utf8mb4_unicode_ci. El esquema documentado contiene 18 tablas base y una vista.
